GLM-5.3: what a 141-shard GlmMoeDsa checkpoint actually ships

31 August 2026 · 3 sources

GLM-5.3 is Z.ai's open-weights text-generation model, a mixture-of-experts architecture with a learned sparse-attention indexer, distributed as 141 safetensors shards under a custom licence. This is for engineers deciding whether to pull it, host it, or fine-tune it, and who want to know how the repository is organised before committing the bandwidth.

What this model is

GLM-5.3 is a conversational text-generation model published by zai-org on the Hugging Face Hub. Its architecture class is GlmMoeDsaForCausalLM and its model type is glm_moe_dsa, which places it in the GLM mixture-of-experts family rather than the dense GLM line. It declares English and Chinese, targets the transformers library, and carries an arxiv:2602.15763 tag pointing at an associated paper.

The model card is explicit that this is not a new pretrain: GLM-5.3 uses the same base model as GLM-5.2, and every gain comes from post-training. That framing matters for how you evaluate it. If you already have infrastructure sized for GLM-5.2, the shape of the model is the same lineage; what changed is behaviour on coding and long-horizon agentic tasks, which is a post-training property and therefore more sensitive to prompt format, tool-calling conventions, and sampling settings than a base-model change would be.

The card claims a 50 percent improvement over GLM-5.2 on an in-house Z.ai Code Bench, plus open-source state of the art on Terminal Bench 3.0 and Agents' Last Exam. The published table is more informative than the headline. Terminal Bench 3.0 moves from 4.6 to 28.3 against GLM-5.2, SWE-Marathon (v1.1) from 19.4 to 42.5, DeepSWE (v1.1) from 46.2 to 66.9. On several of those same rows the closed models still lead: GPT-5.6 Sol takes Terminal Bench 3.0 at 34.6 and DeepSWE at 72.7, Opus 4.8 takes NL2Repo at 69.7 and SWE-Marathon at 48.8, Fable 5 takes FrontierSWE at 88.2. The one row where GLM-5.3 is the bolded leader in the excerpt is CyberGym at 84.5.

Why it is trending now

The numbers are modest in absolute terms and interesting in shape: 1383 likes and 66,195 downloads in the last thirty days, with the repository last modified on 2026-08-31. For a model of this size, downloads are a weak proxy for users, since a single serving deployment pulls the whole shard set and one CI job can do it repeatedly.

The attention driver is the coding and agentic jump described above, arriving from post-training on an existing base. The card also flags what it calls emergent cyber capability, saying capability in that area developed faster than expected as post-training scaled, that the model is state of the art on CyberGym for vulnerability discovery, and that gains are largest further up the exploitation chain, where it more than doubles GLM-5.2 on exploitation benchmarks. Whatever you make of the claim, a vendor volunteering that its open-weights release is strongest at exploitation is a fact worth carrying into your own risk review rather than skipping past.

What the artifact actually contains (weights, config, licence)

The repository holds 154 files, of which 141 are weight shards. That leaves roughly a dozen files for everything else: config, tokenizer, generation settings, and the card. In practice the whole repository is the weights, and any tooling you write against it should assume a sharded safetensors load with an index, not a single file.

The config excerpt tells you most of what shapes your serving decision. Weights are bfloat16. Hidden size is 6144 with an intermediate size of 12288, head_dim is 192, the activation is silu, and attention_bias and attention_dropout are off. Attention uses a compressed KV path with kv_lora_rank of 512. max_position_embeddings is 1048576, so the positional configuration is built for very long context, which is a separate question from whether your serving stack can afford the KV memory to use it.

The distinctive part is the DSA indexer, which is where the name glm_moe_dsa comes from. There is a separate indexer with index_n_heads of 32 and index_head_dim of 128, selecting index_topk of 2048, with index_topk_freq of 4 and index_skip_topk_offset of 3. indexer_rope_interleave is true and index_share_for_mtp_iteration is true, the latter suggesting a multi-token-prediction path that reuses the same index. The indexer_types list alternates: the first three entries are full, then the pattern settles into one full followed by three shared, repeating. So most layers reuse a shared index and only every fourth recomputes it, which is consistent with index_topk_freq of 4. That is the mechanism by which long-context attention is made affordable, and it is also the part most likely to be unsupported or subtly wrong in a runtime that has not explicitly implemented it.

The MoE structure is visible in outline. first_k_dense_replace is 3 and mlp_layer_types begins with three dense entries before switching to sparse, so the early layers are dense and the rest are expert layers. ep_size is 1, meaning the config as published does not assume pre-sharded expert parallelism; your serving stack sets that. The excerpt is truncated before expert count, top-k routing, and layer count, so those are not stated here. Read the full config before sizing hardware.

The licence is declared as other, with license_name glm-5.3. It is a custom licence, not one of the standard SPDX identifiers, and its terms are not reproduced in the material available here. There are three eos_token_id values rather than one, which is typical of chat and tool-calling formats and is a common source of runaway generations if your client only honours a single stop token.

How you would run or fine-tune it

The library tag is transformers and the pipeline tag is text-generation, so the standard AutoModelForCausalLM path is the declared entry point. The practical question is whether the transformers version you have registers glm_moe_dsa and GlmMoeDsaForCausalLM. A custom model type means an older install will fail to resolve the architecture, and a version that resolves the class but has an incomplete DSA implementation is the worse failure, because it produces output rather than an error. Pin and verify the version before drawing conclusions about model quality.

For serving, treat the sparse indexer as the compatibility question. Throughput on a model like this depends on the runtime having real kernels for both expert routing and the top-k index path; a generic fallback will run and will be slow. ep_size of 1 in the config means expert placement is yours to configure, so plan the expert-parallel and tensor-parallel layout deliberately rather than accepting defaults. The bfloat16 dtype and 141-shard layout mean the download and the load are both substantial, and a shared, warmed model cache is worth setting up before you have several nodes pulling independently.

Fine-tuning follows from the same facts. Full-parameter tuning of a bf16 MoE of this shape is an infrastructure project, not a script. Adapter-based tuning is the realistic route for most teams, and on an MoE you should decide explicitly whether adapters attach to attention only or also to expert MLPs, since routing behaviour is part of what post-training shaped here. Given the card's own statement that the gains over GLM-5.2 come entirely from post-training, aggressive fine-tuning is exactly the operation most likely to erode the thing you selected the model for. Establish your evaluation before you tune, not after.

Limits and licence conditions to check before shipping it

The licence is the first blocker. It is declared as other with the name glm-5.3, so no assumption from an Apache or MIT release carries over. Read the actual licence text in the repository and confirm commercial use, redistribution, derivative and fine-tuned weight terms, attribution, and any use restrictions, before it reaches a production plan. If your organisation has a licence review process, this is a case for it rather than a self-serve decision.

Second, take the cyber capability claim at face value operationally. The card states the model is state of the art on CyberGym at 84.5 and that its largest gains are on exploitation benchmarks. If you expose this model to untrusted input, or give it tool access in an environment with real credentials or network reach, the threat model is not the same as for a general chat model. Sandboxing and tool-permission design should be settled before deployment, not retrofitted.

Third, mind the gap between benchmark leadership and your workload. On most rows in the published table GLM-5.3 trails at least one closed model, and the benchmarks that improved most are agentic coding evaluations whose scores are sensitive to scaffold, prompt format, and tool interface. Reproducing a table number requires reproducing the harness. Run your own task set.

Finally, the mechanical details that break deployments: honour all three eos_token_id values, confirm your runtime genuinely supports the DSA indexer and MoE routing rather than silently degrading, and do not assume the 1048576 position limit is a usable context length on your hardware. It is a configuration ceiling, and the memory to reach it is a separate budget.
