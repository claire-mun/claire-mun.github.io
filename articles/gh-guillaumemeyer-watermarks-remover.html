watermarks-remover: 스킬은 얇게, 무거운 일은 로컬 HTTP 서비스로 分離한 구조

2026년 09월 01일 · 출처 3곳

AI 생성 콘텐츠에 붙는 provenance 표식을 텍스트와 파일에서 제거하는 MIT 라이선스 Python 프로젝트입니다. 에이전트 스킬과 실행 서비스를 분리한 설계, 그리고 저장소 파일 분포가 드러내는 우선순위에 관심 있는 엔지니어를 위한 글입니다.

01이게 무엇인가

guillaumemeyer/watermarks-remover는 저장소 설명 그대로 "A privacy-first app that strips AI watermarks from content you own"입니다. 자기가 소유한 콘텐츠에서 AI 출처 표식(provenance mark)을 걷어내는 것이 목적입니다.

구조상 핵심은 두 덩어리로 나뉜다는 점입니다. 하나는 에이전트 스킬(skills/remove-ai-marks/), 다른 하나는 stdlib Python으로 작성된 서비스(service/)입니다. README는 스킬을 thin client라고 부릅니다. 스킬 자체는 코드를 담지 않고 markdown만 배포되며, 실제 처리는 HTTP로 서비스에 넘깁니다. 그래서 에이전트를 띄우는 호스트 쪽에는 Python이 필요 없습니다.

처리 대상은 README의 표에서 세 층으로 정리됩니다. Layer A는 invisible Unicode, exotic spaces, bidi, tag chars 같은 것으로, 결정적(deterministic) Python 스크립트가 담당합니다. Layer B는 토큰 샘플링 기반 통계적 텍스트 워터마크로, 에이전트의 rewrite와 선택적인 rewrite_text.py 훅이 담당합니다. Files 층은 C2PA / EXIF / XMP / 문서 속성을 다루며 PNG, JPEG, WebP, AVIF, HEIC, BMP, GIF, TIFF, SVG, PDF, DOCX, XLSX, PPTX, EPUB, ODT, HTML, Markdown, MP4/MOV/M4A/M4V, WAV, MP3, FLAC를 대상으로 명시합니다. 벤더는 클래스 수준에서 Claude, Gemini / SynthID-Text, OpenAI provenance surfaces, 그리고 open-LLM 쪽 Kirchenbauer 계열 green-list와 keyed-Gumbel / EXP(Aaronson) 표식을 든다고 적혀 있습니다.

02지금 주목받는 이유

스타는 20053개, 열린 이슈는 9개입니다. 마지막 푸시는 2026-09-02T17:53:47Z이고, README가 가리키는 최신 릴리스는 v0.6.0입니다. 스타 규모에 비해 열린 이슈가 9개라는 조합은 이슈 트래커가 논의 창구로 쓰이지 않거나, 정리가 비교적 촘촘하게 이뤄진다는 신호로 읽을 수 있습니다.

주제 자체가 시의성을 갖습니다. Layer A가 다루는 invisible Unicode 계열은 결정적으로 탐지·제거가 가능한 반면, Layer B가 겨냥하는 통계적 워터마크는 생성 시점의 토큰 샘플링에 신호를 심는 방식이라 성격이 다릅니다. 한 저장소가 이 둘을 같은 인터페이스 뒤에 두고, 파일 메타데이터까지 함께 묶은 점이 눈에 띄는 부분입니다.

프로젝트는 이름을 옮긴 이력도 밝힙니다. 이전 이름은 remove-claude-marks였고, /remove-claude-marks 슬래시 별칭은 여전히 문서에 남아 있습니다. 단일 벤더에서 다중 벤더로 범위를 넓힌 흔적입니다.

03어떻게 구성돼 있나

추적 파일은 277개입니다. 그중 benchmarks/ 아래가 99개로 가장 큰 하위 트리이고, tests/ 아래가 72개, service/ 아래가 48개, skills/ 아래가 17개입니다. 이 배열이 프로젝트의 성격을 그대로 보여줍니다. 실제 구현이 들어 있는 service/보다 benchmarks/와 tests/가 각각 더 큽니다. 즉 이 저장소에서 코드보다 무거운 것은 "제대로 지워졌는지 확인하는 장치"입니다.

확장자 분포도 같은 이야기를 합니다. 가장 많은 종류는 .txt 104개와 .py 104개로 정확히 같은 수이고, 이어서 .md 27개, .sh 8개입니다. .txt가 .py와 나란히 최상위에 있다는 것은 대량의 텍스트 픽스처, 즉 표식이 박힌 입력과 기대 출력 같은 코퍼스가 저장소에 함께 들어 있다는 뜻으로 보는 것이 자연스럽습니다. 워터마크 제거는 "돌아간다"만으로는 검증되지 않고 원문과의 대조가 필요하니, 이런 형태가 되는 것이 합리적입니다.

.md 27개는 스킬이 markdown으로만 배포된다는 설계와 맞물립니다. skills/ 아래 17개 파일이 코드 없이 에이전트에게 절차를 지시하는 문서라면, 나머지 .md는 README와 문서류로 흩어져 있을 것입니다. .sh 8개는 설치와 CI 보조 스크립트 규모로는 작은 편입니다.

샘플로 저장소 안에서 확인되는 경로와 파일은 skills/remove-ai-marks/, service/, rewrite_text.py, 그리고 CI 배지가 가리키는 .github/workflows/ci.yml입니다. README 상단의 아스키 로고조차 figlet 명령과 .figlet 디렉터리를 주석으로 남겨 재생성 방법을 적어두는 방식입니다.

04실제로 어떻게 쓰는가

설치 흐름은 두 단계입니다. markdown뿐인 스킬을 설치하고, 서비스를 띄웁니다. 서비스 주소가 기본값인 http://127.0.0.1:8765가 아니면 WATERMARKS_SERVICE_URL 환경 변수로 지정합니다.

Claude Code에서는 저장소에 함께 들어 있는 plugin marketplace를 쓰는 것이 가장 빠른 경로라고 README가 안내합니다. clone이 필요 없고 제자리에서 갱신됩니다. 다른 호스트에서는 하나의 installer가 지원 대상 전부를 덮으며, Python 3.10 이상을 요구합니다. 발췌가 여기서 끊기므로 installer의 구체적인 호출 형태는 확인되지 않습니다.

Layer A와 Files 층은 서비스 쪽 스크립트가 결정적으로 처리하지만, Layer B는 성격이 다릅니다. 에이전트가 텍스트를 다시 쓰는 방식이고 rewrite_text.py 훅은 선택 사항입니다. 통계적 워터마크 제거를 자동화된 파이프라인의 한 단계로 넣으려 한다면, 이 층만은 결정적 변환이 아니라는 점을 전제로 설계해야 합니다.

05무엇을 못 하는가, 어디를 조심해야 하나

범위가 문서에 못 박혀 있습니다. 대상은 "content you own", 즉 본인이 소유한 콘텐츠입니다. 타인의 저작물이나 출처 표기가 요구되는 맥락에서 표식을 제거하는 용도는 프로젝트가 내세우는 용례가 아닙니다.

기술적으로는 Layer B가 가장 약한 고리입니다. 재작성 기반이므로 원문 의미와 문체가 보존된다는 보장이 없고, 제거 성공 여부도 이진적으로 판정되지 않습니다. 벤더 지원 역시 "class-level"이라고 명시돼 있습니다. Claude, Gemini / SynthID-Text, OpenAI, open-LLM 계열 방식군을 겨냥한다는 뜻이지 특정 제품의 현재 구현을 개별적으로 보장한다는 뜻이 아닙니다.

운영 측면에서는 서비스가 별도 프로세스라는 점이 그대로 실패 지점이 됩니다. 스킬은 HTTP 클라이언트일 뿐이라 서비스가 죽어 있거나 포트가 다르면 아무것도 처리되지 않습니다. 마지막으로, 이 글은 저장소 메타데이터와 README 발췌만을 근거로 한 것이고 실행이나 벤치마크로 확인한 내용은 없습니다. benchmarks/ 아래 99개 파일이 무엇을 어떤 기준으로 측정하는지는 직접 열어봐야 알 수 있습니다.
