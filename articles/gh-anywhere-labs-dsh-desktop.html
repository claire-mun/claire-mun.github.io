DSH Desktop: an Electron-era plugin host where the desktop shell is itself a plugin

31 August 2026 · 4 sources

anywhere-labs/dsh-desktop is a community-built Windows and macOS client that wraps DeepSeek Harness's local web UI, host service, and plugin system in a native app. It matters if you are evaluating plugin-host architectures, or considering shipping a plugin into someone else's desktop runtime.

What it is

DSH Desktop packages DeepSeek Harness — its local web UI, host service, and plugin system — into a desktop application for Windows and macOS. The repository is TypeScript, MIT-licensed, and was last pushed on 2026-08-30. The distributed artifacts are an NSIS installer for Windows x64 and a Universal DMG for macOS; the README's stated goal is that no additional runtime setup is needed.

The README is explicit that the project pins a specific upstream version and runs it as-is. What DSH Desktop adds on top is the native shell: windows, tray, terminal, update handling, and workspace configuration. Everything beyond that is expected to arrive through the plugin mechanism that DeepSeek Harness already provides. The project's own slogan states the design constraint directly: everything is a plugin, and the desktop is a plugin too.

The README carries a prominent disclaimer. This is an independent community project with no affiliation, partnership, authorization, or endorsement from DeepSeek, and it states that no DeepSeek employees or upstream DeepSeek Harness team members participate in the repository. Upstream names visible in GitHub's contributor list are inherited from fork history and synced commits.

Why it is getting attention now

22,374 stars on a project whose entire premise is repackaging someone else's runtime says something about where the demand is: people want a local model harness they can install rather than assemble. The download path in the README is a hosted site, not a build-from-source walkthrough, and the primary README is Chinese with an English translation as the secondary document — this is first a Chinese-language desktop client, second an English-language open source project.

There are 299 open issues. For a project of this size that is neither alarming nor reassuring on its own, but it does indicate the repository is being used as a real support channel rather than a code drop. The README also links a "plugin ecosystem manifesto," which frames the project's ambition as growing third-party plugins rather than growing the desktop app itself.

How it is put together (use the file counts and the sample unit)

There are 866 tracked files, and four directories account for most of them: dsh-plugin-desktop/ at 312, vendor/ at 242, dsh-community-market/ at 107, and .agents/ at 69. The shape of that distribution is the story. The desktop shell is not the application with plugins bolted on — it lives in dsh-plugin-desktop/, a directory named like any other plugin, and it is the largest single unit of source. The slogan is a literal description of the directory layout.

The file-type counts sharpen this. There are 297 .ts files and 241 .tgz files. Given vendor/ holds 242 files, vendor/ is almost entirely packed npm tarballs committed into the repo. That is a deliberate choice consistent with the README's claim of pinning and running a specific upstream version verbatim: rather than resolving upstream packages from a registry at build time, the exact bytes are checked in. 110 .md and 45 .yaml files round out the tree — a documentation-heavy project with meaningful configuration surface. The 69 files under .agents/ indicate AI coding-agent instructions are themselves a tracked, versioned part of the codebase.

The sample unit is dsh-community-market/src/client/index.ts, and it shows the plugin contract clearly. A plugin exports `inject` (here, `['slots', 'locale']`) declaring the host services it requires, plus an `apply(ctx)` function that receives a cordis Context. Inside `apply`, the plugin registers a locale dictionary under a namespace constant, installs its styles, and injects components into named extension points — `settings.plugins.tab` and `sidebar.footer.action` — each with an id and an explicit `order`. Registrations are wrapped in `ctx.effect(...)` with a human-readable label, so setup has a matching teardown and the plugin can be unloaded. Notably, the file's imports of sibling packages like `@deepseek-ai/dsh-client-ui-conversation/client` are bare `import type {}` statements: they pull in ambient type augmentation only, not runtime code. The plugin also uses `declare module` to extend the host's `LocaleNamespaceMap` with its own key. Coupling between plugins is expressed in the type system rather than in imports.

How you would actually use it

As a user, you download the Windows installer or the macOS DMG from the project's site and run it; the README points at a user guide and an FAQ for plugin commands and troubleshooting.

As a developer, the interesting entry point is writing a plugin, and dsh-community-market/src/client/index.ts is a usable template. You declare your service dependencies in `inject`, register UI into named slots with an explicit ordering value, register locale dictionaries under a namespace (the sample ships zh and en), and wrap every side effect in `ctx.effect` so it can be reversed. If your plugin needs types from other plugins' contributions, you import them as types only.

The slot names in the sample are worth reading as a map of where third-party code is allowed to appear: a tab in the plugin settings pane and an action in the sidebar footer. Extension points are enumerated and named by the host, not discovered dynamically, so what you can build is bounded by which slots exist.

What it does not do, or where you would be careful

The vendored tarballs are the main thing to think hard about. 241 committed .tgz files give you reproducibility and an exact upstream pin, but they are opaque in diffs, they cannot be audited by reading the repository, and updating them is a manual act rather than a lockfile bump. If you plan to build from source or ship this internally, budget time for verifying what is inside vendor/ and for tracking the licenses of what is vendored — the MIT license on this repository covers this repository's own code.

Be precise about provenance when explaining this to others. The README states the project is unaffiliated with DeepSeek and that upstream-looking contributors are a fork-history artifact. Anyone reading the GitHub contributor list as evidence of upstream involvement will draw the wrong conclusion, and the maintainers say so themselves.

The installer table covers Windows x64 and macOS Universal only. Documentation is Chinese-first with an English README as a secondary path, so expect the deepest material — the user guide, the FAQ, the ecosystem manifesto — to be most complete in Chinese. Finally, the README's own release and download badges point at anywhere-labs/deepseek-harness-desktop while the repository is anywhere-labs/dsh-desktop; if you script against either name, confirm which one is canonical before depending on it.
