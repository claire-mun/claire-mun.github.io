anydoc: 오피스 문서를 Markdown으로 바꾸는 Rust 라이브러리의 구조 읽기

2026년 09월 01일 · 출처 3곳

Word, PowerPoint, Excel, OpenDocument, RTF, EPUB, CSV, PDF를 GitHub-Flavored Markdown으로 변환하는 Rust 라이브러리입니다. LLM 파이프라인 앞단에서 문서 파싱을 직접 처리해야 하는 엔지니어, 그리고 파서 테스트를 어떻게 조직해야 하는지 참고할 사람에게 의미가 있습니다.

01이게 무엇인가

anydoc은 Firecrawl이 만든 문서 변환 라이브러리입니다. 입력은 Word, PowerPoint, Excel, OpenDocument, RTF, EPUB, CSV, PDF이고 출력은 GitHub-Flavored Markdown 한 가지입니다. 저장소 설명과 README가 강조하는 지점은 포맷별로 다른 결과를 내지 않는다는 것, 즉 어떤 포맷이 들어와도 하나의 일관된 출력 형태를 유지한다는 점입니다.

핵심은 Rust로 작성돼 있고, 그 위에 Node.js, Python, 그리고 브라우저용 WebAssembly 바인딩이 얹혀 있습니다. 배포 채널도 그에 맞춰 crates.io, npm(@firecrawl/anydoc), PyPI(firecrawl-anydoc)로 나뉩니다. 라이선스는 MIT입니다.

용도는 README에 명시돼 있습니다. 오피스 문서를 LLM이 읽을 수 있는 Markdown으로 바꾸는 것이고, 같은 변환을 서비스로 제공하는 Firecrawl Parse의 기반이기도 합니다. 직접 실행하지 않으려면 호스팅 API를 쓰라는 선택지를 README가 직접 안내합니다.

02지금 주목받는 이유

스타는 20005개, 열린 이슈는 79개, 마지막 푸시는 2026-08-28T02:13:16Z입니다. 활발히 손이 가고 있는 저장소입니다.

관심이 몰리는 배경은 문서 파싱이 RAG와 에이전트 파이프라인의 실질적인 병목 구간이라는 점입니다. 지금까지 이 자리는 대체로 Python 생태계의 조합으로 채워졌는데, anydoc은 단일 Rust 코어에 언어별 바인딩을 붙이는 방식을 택했습니다. 같은 파싱 로직을 서버, CLI, 그리고 브라우저에서 그대로 쓸 수 있다는 뜻입니다.

또 하나는 배포 형태입니다. anydoc은 Agent Skill로도 패키징돼 있어서 npx skills add firecrawl/anydoc 한 줄로 에이전트에 붙습니다. Claude Code, Codex, Cursor, OpenCode 등에서 동작한다고 README가 밝히고 있습니다. 라이브러리를 코드에 링크하는 것과 에이전트에게 도구로 쥐여주는 것을 같은 저장소가 동시에 겨냥하고 있습니다.

03어떻게 구성돼 있나

추적 파일은 329개입니다. 이 중 tests/ 아래가 149개, src/ 아래가 76개, fuzz/ 아래가 33개, node/ 아래가 15개입니다. 구현보다 테스트 쪽 파일이 더 많다는 배치이고, 파서 프로젝트로서는 자연스러운 무게중심입니다.

파일 종류를 보면 성격이 더 분명해집니다. .rs가 100개, .snap이 66개, .docx가 20개, .md가 12개입니다. .snap 66개는 스냅샷 테스트 결과물입니다. 변환 결과를 사람이 눈으로 확인한 뒤 고정해 두고, 이후 커밋이 그 출력을 바꾸면 diff로 드러나게 하는 방식입니다. Markdown 출력처럼 '정답'을 단정하기 어렵지만 회귀는 반드시 잡아야 하는 대상에 잘 맞습니다. .docx 20개는 저장소 안에 직접 들어 있는 입력 픽스처로, 바이너리 문서를 커밋해 두고 스냅샷과 짝지어 돌리는 구조를 시사합니다.

fuzz/ 아래 33개 파일은 이 프로젝트가 무엇을 두려워하는지 보여줍니다. docx나 pptx는 결국 압축된 컨테이너 안의 XML이고, 깨진 입력이나 악의적으로 조작된 입력이 파서를 넘어뜨릴 수 있습니다. 퍼징 타깃을 별도 디렉터리로 유지한다는 것은 정상 문서의 변환 품질과 비정상 입력에 대한 견고함을 따로 관리하고 있다는 뜻입니다.

node/ 아래는 15개 파일입니다. 바인딩 계층이 얇게 유지되고 있고, 로직이 코어에 있다는 신호로 읽힙니다. .rs 100개 중 src/ 아래가 76개이므로 나머지 Rust 코드는 퍼징 타깃과 바인딩 쪽에 흩어져 있는 셈입니다.

04실제로 어떻게 쓰는가

가장 가벼운 진입점은 CLI입니다. npx @firecrawl/anydoc report.docx는 Markdown을 stdout으로 내보내고, -o 옵션으로 파일에 씁니다. 하이픈과 --format csv를 조합하면 stdin을 읽습니다. npx는 첫 실행에서 플랫폼에 맞는 미리 빌드된 바이너리를 내려받습니다. 상시 명령이 필요하면 npm install -g @firecrawl/anydoc으로 전역 설치하라고 안내합니다.

Node.js에서는 npm install @firecrawl/anydoc 후 toDocument, toMarkdown, toMarkdownBytes를 가져다 씁니다. 파일 경로를 받는 형태와 바이트를 받는 형태가 갈라져 있어서, 디스크를 거치지 않고 업로드 스트림을 그대로 넘기는 경로가 열려 있습니다.

에이전트에 붙이는 경로는 앞서 말한 skills 설치이고, 스킬 정의는 skills/convert-documents-to-markdown/SKILL.md에 있습니다. 브라우저에서 먼저 확인하고 싶다면 데모 페이지가 라이브러리를 WebAssembly로 실행하므로 파일이 로컬에 머무릅니다.

05무엇을 못 하는가, 어디를 조심해야 하나

가장 분명한 한계는 스캔된 문서입니다. README가 직접 인정하듯 anydoc 혼자서는 스캔된 페이지를 읽지 못합니다. --ocr hosted 옵션은 Firecrawl Parse로 넘겨 OCR 모델을 태우는 경로이고, 이 시점에서 문서가 외부 서비스로 나갑니다. 로컬 처리라는 전제가 옵션 하나로 뒤집히는 지점이므로, 민감한 문서를 다루는 파이프라인이라면 OCR 경로를 켤 때 무엇이 어디로 가는지 분명히 해두는 편이 좋습니다.

출력 포맷이 하나로 고정돼 있다는 점도 양날입니다. 일관된 Markdown은 LLM 입력으로는 장점이지만, 원본의 레이아웃, 병합 셀, 각주, 도형 배치 같은 정보는 그 과정에서 평탄해집니다. 표가 많은 재무 문서나 슬라이드처럼 위치 자체가 의미인 자료라면, 변환 결과를 실제 문서 샘플로 직접 확인한 뒤 판단해야 합니다.

성능에 관해 README는 한 자릿수 밀리초를 이야기하지만, 이는 프로젝트 측 서술이고 어떤 문서와 어떤 환경 기준인지는 위 발췌만으로 확인되지 않습니다. 도입을 검토한다면 본인 문서 분포로 직접 재보는 편이 안전합니다. 열린 이슈 79개도 함께 훑어볼 만한 지표입니다.
