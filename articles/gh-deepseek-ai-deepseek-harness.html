DeepSeek Harness: '모든 것이 플러그인'이라는 구조가 저장소에 남긴 흔적

2026년 09월 01일 · 출처 4곳

DeepSeek AI가 공개한 오픈소스 에이전트 하네스 dsh는 Cordis 위에서 모든 기능을 플러그인으로 취급하는 구조를 택했습니다. 에이전트 실행 환경을 직접 조립하거나, 샌드박스·플러그인 경계를 어떻게 그을지 고민하는 엔지니어에게 참고가 되는 사례입니다.

01이게 무엇인가

DeepSeek Harness는 DeepSeek AI가 개발한 오픈소스 에이전트 하네스이고, CLI 이름은 dsh입니다. 저장소 설명 한 줄은 "DeepSeek Harness: Everything is a Plugin."이고, README도 everything-is-a-plugin 아키텍처라고 명시합니다. 즉 특정 기능을 코어에 넣고 나머지를 확장으로 붙이는 구조가 아니라, 기능 단위 자체가 처음부터 플러그인이라는 전제 위에 서 있습니다.

기반은 Cordis입니다. README는 Cordis의 설계가 논문 'A Programming Paradigm for Spatiotemporal Composability'(arXiv:2608.25512)에 기술돼 있다고 밝힙니다. 하네스가 자체 플러그인 규약을 발명하는 대신, 시간·공간적 합성 가능성을 다루는 별도 런타임을 빌려 쓴다는 뜻입니다.

주 언어는 TypeScript, 라이선스는 MIT입니다.

03어떻게 구성돼 있나

추적 파일은 8876개입니다. 이 중 packages/ 아래가 4479개로 절반 가까이를 차지합니다. 플러그인이 곧 패키지라는 구조를 파일 분포가 그대로 보여줍니다.

그다음이 .agents/ 2596개입니다. 에이전트 정의가 코드와 나란히, 그러나 별도 최상위 디렉터리로 분리돼 관리되고 있다는 신호입니다. snapshots/ 658개는 출력이나 상태를 스냅샷으로 고정해 비교하는 방식이 저장소 차원에서 자리 잡았음을 시사합니다. docs/는 360개입니다.

확장자 분포도 같은 이야기를 합니다. .md가 2856개로 가장 많고, .ts가 2819개로 거의 같은 수, 그다음이 .yaml 1291개와 .json 717개입니다. 문서와 마크다운 형태의 정의가 코드와 대등한 비중을 차지하고, 설정은 YAML과 JSON으로 흩어져 있습니다.

샘플로 볼 만한 파일은 native/landlock-run/packages/entry/src/index.ts입니다. 미리 빌드된 landlock-run 런처를 감싸는 JavaScript API로, 호스트에 맞는 바이너리를 고르고 grant argv를 만들고 기능 프로브를 실행합니다. 주석은 이 모듈이 런처의 CLI 계약(docs/cli-contract.md)을 소유하므로 소비자가 런처 출력을 직접 파싱하거나 플래그를 손으로 적을 일이 없다고 설명합니다. 계약과 바이너리가 하나의 패키지 계열로 함께 버전이 매겨지기 때문에 프로브 파싱이 바이너리와 어긋나는 일이 구조적으로 불가능해진다는 것입니다. 정책은 소비자 쪽에 남습니다. 이 패키지는 '샌드박스 모드'가 무엇인지 알지 못하고, 어떤 경로에 읽기 또는 쓰기가 허용되는지만 압니다. 플러그인 경계를 어디에 긋는지 보여주는 구체적인 예입니다.

04실제로 어떻게 쓰는가

가장 짧은 경로는 npm입니다. Node.js를 설치한 뒤 npx @deepseek-ai/dsh web을 실행하면 됩니다. 이 명령은 기본적으로 http://127.0.0.1:3080 에 Web UI를 띄우고, 로컬 실행이면 기본 브라우저를 함께 엽니다. SSH로 실행한 경우에는 호스트 URL만 출력하는데, 포워딩된 로컬 주소는 SSH 클라이언트나 에디터가 소유하기 때문입니다. 브라우저를 열지 않으려면 --no-open을 넘깁니다.

저장소 체크아웃에서 돌리려면 git clone 후 pnpm install, pnpm run build, pnpm dsh web 순서입니다. pnpm run build가 저장소 산출물을 준비하고, pnpm dsh web은 다시 빌드하지 않고 그 산출물을 사용합니다.

확장 쪽 관례도 정해져 있습니다. 플러그인 저장소에는 dsh-plugin 토픽을 달아 발견 가능하게 하라고 안내합니다. 개발은 docs/development.md와 docs/architecture.md에서 시작하고, 에이전트가 작업할 때는 AGENTS.md를 따르도록 돼 있습니다.

05무엇을 못 하는가, 어디를 조심해야 하나

developer preview라는 점이 가장 큰 제약입니다. README는 호환성을 깨는 변경이 있을 것이라고 명시하고, 실행 전에 SAFETY.md를 읽으라고 요구합니다. 에이전트 하네스는 정의상 코드 실행과 파일 접근을 다루므로 이 경고는 형식적인 문구로 읽지 않는 편이 낫습니다.

열린 이슈는 0개입니다. 활발한 프로젝트에서 이 숫자는 보통 이슈 트래커를 쓰지 않는다는 뜻이고, 실제로 README는 피드백과 버그 리포트를 GitHub Discussions로 보내라고 안내합니다. 문제를 제보하려면 이슈를 여는 습관 대신 Discussions나 Discord를 찾아가야 합니다.

샌드박스 계층에도 한계가 명시돼 있습니다. landlock-run의 프로브는 호스트에 대해 세 가지 판정을 내립니다. 커널이 런처가 통제할 수 있는 모든 접근을 강제하면 full, 오래된 Landlock ABI가 일부만 통제하면 partial, 아무것도 강제할 수 없으면 unusable입니다. 즉 같은 명령이 커널에 따라 다른 격리 수준으로 돌아갑니다. 또한 이 모듈에는 환경 변수 오버라이드가 의도적으로 하나도 없습니다. 어떤 바이너리가 프로세스를 가두는지가 주변 환경에 의해 결정되면 안 된다는 이유이고, 테스트 주입은 함수 파라미터로만 합니다. 운영 환경에서 환경 변수로 샌드박스 동작을 바꾸려는 시도는 통하지 않습니다.

종료 코드 해석에도 주의가 필요합니다. 런처 수준 실패는 사용법 오류, 강제하지 않는 커널, 열 수 없는 grant 루트, exec 실패 모두 125로 나옵니다. 그런데 exec가 성공한 뒤 감싸인 명령 자체가 125를 반환할 수도 있어서, 런처 실패로 단정하려면 런처가 낸 치명적 진단 메시지가 함께 있는지까지 확인해야 합니다.
