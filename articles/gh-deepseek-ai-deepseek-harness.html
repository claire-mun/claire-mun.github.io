DeepSeek Harness: an agent runtime where the plugin graph is the product

01 September 2026 · 4 sources

DeepSeek Harness (`dsh`) is an MIT-licensed, TypeScript agent harness from DeepSeek AI, built on the Cordis plugin framework and shipped as a large monorepo. If you are evaluating agent runtimes to build on rather than just run, the way this repository is partitioned tells you more than the README does.

What it is

DeepSeek Harness is an open-source agent harness developed by DeepSeek AI, distributed on npm as `@deepseek-ai/dsh`. Its one-line description is "Everything is a Plugin," and that is meant literally: the project is built on an everything-is-a-plugin architecture powered by Cordis, whose design is written up in a paper the README links, "A Programming Paradigm for Spatiotemporal Composability."

The primary entry point is a local web UI. Running `npx @deepseek-ai/dsh web` starts a server at http://127.0.0.1:3080 by default and opens a browser for a local launch; an SSH launch only prints the host URL, because the SSH client or editor owns the forwarded local address. A `--no-open` flag suppresses the browser.

The license is MIT, with third-party dependency licenses disclosed separately in THIRD_PARTY_NOTICES.md. The project describes itself as being in developer preview and states plainly that there will be compatibility-breaking changes.

There are 8876 tracked files. The largest single subtree is packages/, at 4479 files — consistent with a monorepo where the harness itself is decomposed into many small published units rather than one core library plus extensions. Next is .agents/ at 2596 files, a top-level directory given roughly comparable weight to the code packages; this is a repository where agent definitions are first-class tracked artifacts, not configuration tucked into a corner. Then snapshots/ at 658 files, and docs/ at 360.

The file-type mix reinforces this. Markdown leads at 2856 files, just ahead of TypeScript at 2819, with YAML at 1291 and JSON at 717. For a project whose primary language is TypeScript, having as much prose as code is unusual, and it lines up with the .agents/ and docs/ trees: prompts, agent specs, and contracts are the substance, not annotation. The YAML and JSON volume suggests declarative plugin manifests and fixtures carrying a lot of the wiring.

The sample unit shows what "everything is a plugin" costs and buys at the leaf level. native/landlock-run/packages/entry/src/index.ts is a JavaScript API over a prebuilt Landlock launcher binary — note the nesting: a native component that is itself a packages/ tree. Its module docstring states that the package owns the launcher's CLI contract, documented in docs/cli-contract.md, so consumers never parse launcher output or spell launcher flags themselves; the contract and the binaries version together in one package family, making probe-parsing drift against the binary structurally impossible. It exports LAUNCHER_BIN and LAUNCHER_FAILURE_EXIT, the latter being 125, the exit code for every launcher-level failure — usage error, unenforcing kernel, unopenable grant root, failed exec. Because a wrapped command may also return 125 after a successful exec, consumers must additionally require a matching launcher-owned fatal diagnostic to attribute the failure to the launcher.

Two design commitments are stated explicitly in that same file and are worth generalising from. First, policy stays with the consumer: the package does not know what a "sandbox mode" is, only which paths are granted read or write. Second, there are deliberately no environment-variable overrides anywhere in the module, on the grounds that which binary confines a process must never be decidable by the ambient environment; test injection is by function parameter instead. That is a boundary drawn against configurability on purpose, which is a reasonable thing to expect elsewhere in a codebase organised this way.

How you would actually use it

The npm path is the fast one: install Node.js, run `npx @deepseek-ai/dsh web`, and work in the web UI. The user-facing documentation for that is docs/user/guide/index.md, with a hosted documentation site at https://deepseek-harness.github.io/deepseek-harness/.

From a checkout, the sequence is `git clone`, `pnpm install`, `pnpm run build`, then `pnpm dsh web`. The distinction the README draws matters in a monorepo this size: `pnpm run build` prepares the repository artifacts, and `pnpm dsh web` uses those built artifacts without rebuilding. If you are iterating on a package, you own the rebuild step.

If you are writing a plugin, the README asks you to tag your repository with the `dsh-plugin` GitHub topic for discoverability. For working on the harness itself, the starting points are docs/development.md and docs/architecture.md, plus CONTRIBUTING.md; there is also an AGENTS.md that the README directs agents to follow, which is consistent with the size of the .agents/ tree.

What it does not do, or where you would be careful

Take the developer-preview warning at face value. The project states in bold that there will be compatibility-breaking changes, and in a monorepo where the plugin surface is spread across a packages/ tree of 4479 files, breaking changes can land in units you depend on without touching anything you would think to watch. Pin versions, and expect the plugin API to move.

The sandbox story is partial by construction, and the code says so. The Landlock probe reports `full` when the running kernel enforces every access the launcher can govern, `partial` when an older Landlock ABI governs only a subset — still confined for everything it supports — and `unusable` when nothing can be enforced, such as on a kernel without Landlock. Landlock is Linux-specific, so on other hosts you should not assume this layer is doing anything for you, and you should read SAFETY.md before running the harness against anything you care about.

Finally, the intake channel: with open issues at 0 and feedback directed to GitHub Discussions and Discord, there is no public issue backlog to search before you hit a problem. That removes the usual way of checking whether a bug is known, and is worth factoring into how much of your own diagnosis you plan to do.
