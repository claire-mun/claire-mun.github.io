DeepSeek-V4-Flash-Vision-Exp: config.json으로 읽는 실험적 멀티모달 MoE의 구조

2026년 09월 01일 · 출처 3곳

DeepSeek-V4 계열의 첫 실험적 멀티모달 모델로, fp8로 저장된 48개 샤드와 비표준 설정 키가 다수 섞인 MoE 리포지토리입니다. 장문맥 sparse attention, MoE 라우팅, 저정밀도 서빙 스택을 직접 다루는 엔지니어라면 config 구조만으로도 볼 것이 있습니다.

01이 모델이 무엇인가

deepseek-ai가 공개한 image-text-to-text 모델입니다. library는 transformers, license는 mit, 마지막 수정은 2026-09-01T09:22:10.000Z입니다. 모델 카드는 이것을 DeepSeek-V4 계열의 첫 실험적 멀티모달 모델이라고 소개하며, DeepSeek-V4-Flash 아키텍처에 visual module을 얹고 continued training으로 시각 이해 능력을 붙였다고 설명합니다.

리포지토리를 읽을 때 먼저 눈에 띄는 것은 이름과 클래스의 불일치입니다. pipeline_tag는 image-text-to-text인데 architectures는 DeepseekV4ForCausalLM 하나이고 model_type은 deepseek_v4입니다. 선언된 태그에도 text-generation과 image-text-to-text가 함께 들어 있습니다. 즉 vision이 별도의 조건부 생성 클래스로 분리된 형태가 아니라, 기존 causal LM 클래스 이름 아래에 들어가 있는 구성입니다.

본체는 MoE입니다. num_hidden_layers는 43, hidden_size는 4096이고, n_routed_experts 256에 n_shared_experts 1, 토큰당 num_experts_per_tok 6을 고릅니다. moe_intermediate_size는 2048, routed_scaling_factor는 1.5이며 topk_method는 noaux_tc, scoring_func는 sqrtsoftplus, norm_topk_prob는 true입니다. 라우팅 스코어 함수와 보조 손실 없는 topk 선택 방식이 config 레벨에서 그대로 노출돼 있습니다.

attention 쪽은 더 특이합니다. num_attention_heads는 64인데 num_key_value_heads는 1이고 head_dim은 512, q_lora_rank와 o_lora_rank는 각각 1024, o_groups는 8, qk_rope_head_dim은 64입니다. 여기에 index_n_heads 64, index_head_dim 128, index_topk 512로 정의된 별도 인덱서 경로가 있고, sliding_window는 128입니다. compress_ratios는 0, 0으로 시작해 4와 128을 번갈아 놓다가 끝에서 4, 0, 0, 0으로 닫히는 레이어별 목록이라, 층마다 압축 강도를 다르게 준 구성임을 알 수 있습니다. 문맥 길이는 max_position_embeddings 1048576이고, rope_scaling은 type yarn에 factor 16, original_max_position_embeddings 65536입니다. rope_theta는 10000, compress_rope_theta는 160000으로 서로 다른 값이 잡혀 있습니다.

02지금 트렌딩에 오른 이유

좋아요는 489, 최근 30일 다운로드는 17893입니다. 공개 시점 기준으로 카드가 내세우는 것은 시각 능력 자체보다 에이전트 성능입니다. DeepSeek-V4-Flash-0731 대비 멀티모달 에이전트 능력이 크게 개선됐고 텍스트 전용 에이전트 작업은 비슷한 수준을 유지한다고 서술합니다.

03실제로 무엇이 들어 있나

저장소 파일은 84개이고 그중 가중치 샤드가 48개입니다. 사실상 리포지토리 대부분이 가중치이며, 샤드가 이 개수로 쪼개져 있다는 것은 인덱스 파일을 따라가는 분할 로딩을 전제한다는 뜻입니다.

수치 포맷이 한 config 안에 세 가지로 섞여 있습니다. quantization_config는 quant_method fp8, fmt e4m3, scale_fmt ue8m0, activation_scheme dynamic, weight_block_size [128, 128]으로 블록 단위 fp8 양자화를 선언합니다. 그런데 expert_dtype은 fp4로 따로 지정돼 있고, torch_dtype은 bfloat16입니다. 선언된 태그에도 8-bit와 fp8이 함께 들어 있습니다. 전문가 가중치와 나머지 가중치의 정밀도가 다르게 잡힌 구조로 읽히므로, 로더가 이 조합을 모두 이해해야 합니다.

그 밖에 표준 transformers config에서 보기 어려운 키들이 있습니다. num_hash_layers 3, hc_mult 4, hc_sinkhorn_iters 20, hc_eps 1e-06 같은 hash 계열 설정과 dspark_block_size 5, 그리고 이름만 보이고 발췌가 끊긴 dspark_noise_token 계열이 그렇습니다. num_nextn_predict_layers는 3으로 multi-token 예측 레이어가 잡혀 있고, swiglu_limit은 10.0, rms_norm_eps는 1e-20, vocab_size는 129280, tie_word_embeddings는 false입니다.

라이선스는 mit입니다. 모델 카드 프론트매터의 license 필드도 mit이고 카드 본문 배지 역시 MIT를 가리킵니다. 발췌 범위 안에서는 이 외에 별도의 사용 제한 조항이 보이지 않습니다.

04어떻게 실행하거나 파인튜닝하는가

config.json의 transformers_version은 5.0.0입니다. model_type deepseek_v4와 DeepseekV4ForCausalLM을 인식하는 빌드가 필요하다는 뜻이고, 위에 적은 hc_*, dspark_*, index_*, compress_ratios 같은 키를 실제로 해석하는 구현이 있어야 선언된 대로 동작합니다. 태그에는 endpoints_compatible이 포함돼 있습니다.

서빙 쪽에서 확인해야 할 것은 정밀도입니다. weight_block_size [128, 128] 기반 fp8 블록 양자화와 ue8m0 스케일 포맷, dynamic activation scheme을 지원하는 런타임이어야 하고, expert_dtype fp4로 선언된 전문가 가중치를 따로 처리할 수 있어야 합니다. 문맥을 1048576까지 쓰려면 yarn factor 16 스케일링과 index_topk 512로 동작하는 sparse attention 경로가 함께 구현돼 있어야 합니다.

파인튜닝에 대해서는 주어진 발췌에 레시피도, 실행 예제도, 명령어도 없습니다. 저장 포맷이 fp8이고 전문가가 fp4로 선언돼 있다는 점만 놓고 보면 일반적인 학습 경로를 그대로 태우기는 어려운 구성이므로, 실제 절차는 리포지토리 원문을 직접 확인하는 편이 맞습니다.

05도입 전에 확인해야 할 한계와 라이선스 조건

이름의 Exp와 카드의 서술이 모두 실험적 모델임을 밝히고 있습니다. 벤치마크 표는 배포자가 직접 제시한 값이고, 발췌 기준으로 Cybergym 행에서 잘려 있어 전체 항목을 확인할 수 없습니다.

구조상 확인이 필요한 지점이 몇 가지 있습니다. 첫째, pipeline_tag는 image-text-to-text인데 architectures는 DeepseekV4ForCausalLM 단일 항목이고, 제공된 config 발췌는 dspark_noise_token 중간에서 끊겨 vision 관련 설정을 직접 확인할 수 없습니다. 이미지 입력 경로가 어느 전처리기와 묶여 있는지는 리포지토리에서 따로 봐야 합니다. 둘째, transformers_version 5.0.0 의존과 비표준 키들 때문에 서드파티 추론 스택 지원 여부가 실질적인 도입 조건이 됩니다. 셋째, torch_dtype bfloat16, quantization_config fp8, expert_dtype fp4가 한 파일에 공존하므로 로더가 어떤 조합을 실제로 적용하는지 확인해야 합니다.

라이선스는 mit이라 조건 자체는 단순합니다. 다만 가중치 배포 라이선스와 별개의 사용 정책이 있는지는 발췌 범위에서 확인되지 않으므로 리포지토리 원문을 보는 것이 안전합니다. 채택 규모는 좋아요 489, 최근 30일 다운로드 17893으로, 운영 환경에서의 사례가 충분히 쌓였다고 보기는 이른 단계입니다.
